# Sentinel 三节点故障切换验证记录

## 1. 拓扑设计

| 节点 | 地址 | 初始 Redis 角色 | Sentinel | 说明 |
| --- | --- | --- | --- | --- |
| 第一台 | `172.20.10.12` | REPLICA | 运行 | `replica-priority=50`，优先提升 |
| 第二台 | `172.20.10.14` | MASTER | 运行 | 本次故障模拟的初始主库 |
| 第三台 | `172.20.10.3` | REPLICA | 运行 | 普通副本 |

三个 Sentinel 使用统一监控名 `mymaster`，初始监控 `172.20.10.14:6379`，`quorum=2`。实验环境的主观下线时间为 5 秒，便于快速验证；生产值需要根据网络抖动、业务超时和故障恢复目标重新确定。

Redis Sentinel 管理的是动态主从拓扑，因此平台不能永远把某一个 IP 当作主库。平台应通过 Sentinel 或任务结果确认当前主库。

## 2. 故障前检查

- 第二台 Redis：`role:master`、`connected_slaves:2`。
- 第一、第三台 Redis：`role:slave`、`master_host:172.20.10.14`、`master_link_status:up`。
- 三个 Sentinel 都返回主库 `172.20.10.14:6379`。
- 每个 Sentinel 都发现另外两个 Sentinel：`num-other-sentinels=2`。
- 三个节点均返回：`OK 3 usable Sentinels. Quorum and failover authorization can be reached`。

## 3. 故障模拟

1. 在初始主库写入 `sentinel:failover:probe=before-failover`。
2. 通过第二台 Agent 执行 `TASK202609290317 STOP_REDIS`。
3. Agent 返回 SUCCESS，确认 Redis 停止且 6379 端口释放。
4. 三个 Sentinel 在约 5 秒后判断原主库主观下线和客观下线。
5. Sentinel 选中优先级更高的第一台副本并将其提升为主库。
6. 第三台被自动改为跟随第一台。

关键 Sentinel 事件如下：

```text
+sdown master mymaster 172.20.10.14 6379
+odown master mymaster 172.20.10.14 6379 #quorum 2/2
+elected-leader master mymaster 172.20.10.14 6379
+selected-slave slave 172.20.10.12:6379
+promoted-slave slave 172.20.10.12:6379
+failover-end master mymaster 172.20.10.14 6379
+switch-master mymaster 172.20.10.14 6379 172.20.10.12 6379
```

## 4. 数据验证

- 新主库第一台可以读取故障前写入的 `before-failover`。
- 在新主库写入 `sentinel:failover:after=new-master-ok` 成功。
- 第三台副本可以同时读取 `before-failover` 和 `new-master-ok`。
- 原第二台恢复并完成同步后，也能读取两份数据。

## 5. 旧主库恢复和配置修正

第一次恢复第二台时，Sentinel 已经把它改成新主库的副本，但复制状态为 `down`。原因是初始主库配置没有 `masterauth`。故障切换后，任何原主库都可能变成副本，因此三台 Redis 都必须配置：

```text
masterauth <REDIS_PASSWORD>
```

修正第二台持久配置后重新启动，最终状态如下：

| 节点 | 最终角色 | 复制状态 |
| --- | --- | --- |
| `172.20.10.12` | MASTER | 两个在线副本 |
| `172.20.10.14` | REPLICA | `master_link_status:up` |
| `172.20.10.3` | REPLICA | `master_link_status:up` |

三个 Sentinel 最终都返回主库 `172.20.10.12:6379`，并且仍有三个可用 Sentinel，自动故障切换和旧主库重新加入均验证成功。

## 6. Agent 需要继续改进的地方

旧主库恢复时，Redis 刚启动的短暂阶段仍显示为 MASTER。当前 `START_REDIS` 根据即时角色完成健康检查，因此任务 `TASK202609290318` 先返回了“启动成功，角色：MASTER”；随后 Sentinel 才把它配置为新主库的副本。

最终拓扑正确，但任务结果过早。建议后续修改任务协议和启动检查：

- 平台在 `START_REDIS` 参数中传入 `expectedRole`。
- 期望为副本时同时传入 `expectedMasterHost` 和 `expectedMasterPort`。
- Agent 等待角色、主库地址和 `master_link_status=up` 连续稳定一段时间后再返回 SUCCESS。
- 平台仍需以三个 Sentinel 对当前主库的共识作为整个切换步骤的最终判断。

本次没有新增 Maven 依赖、插件或第三方运行组件。
